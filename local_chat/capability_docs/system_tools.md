# برنامه‌نویسی محلی (Programming mode)

حالت «برنامه‌نویسی» در کنار «گفت‌وگوی عمومی» فعال می‌شود. در گفت‌وگوی عمومی هیچ ابزاری به مدل داده نمی‌شود.

## آگاهی همیشگی مدل از پروژه‌ها
در **هر** پیام و **هر دور** اجرا، «وضعیت واقعی دیسک» به مدل داده می‌شود: مسیر پوشهٔ پروژه‌ها، پروژهٔ فعال (آخرین پروژهٔ کاری)، فایل‌های واقعی با حجم، وجود venv و کتابخانه‌ها، و فهرست آخرین عملیات انجام‌شده (از `.localchat/manifest.json` خود پروژه). هنگام تغییر یا اجرای طرح، کد فعلی پروژه هم (با اولویت main.py) در هر دور تازه خوانده و داده می‌شود؛ بنابراین مدل بعد از فشرده‌سازی زمینه نام کلاس‌ها و فایل‌ها را فراموش نمی‌کند. ابزار `list_projects` همهٔ پروژه‌ها را نشان می‌دهد. لاگ ابزارهای نوبت‌های قبل به مدل داده نمی‌شود (تا از روی آن‌ها نتیجهٔ ساختگی نسازد)؛ فقط خلاصهٔ فایل‌های ساخته‌شده می‌ماند.

## جریان کار

1. **پرسش درباره توانایی** («می‌تونی بازی بسازی؟») فقط پاسخ و چند سؤال کوتاه می‌گیرد؛ هیچ پروژه‌ای ساخته نمی‌شود.
2. **درخواست روشن** («یک بازی مار با pygame بساز») → مدل یک طرح مرحله‌به‌مرحله می‌دهد. تا تأیید نکنید هیچ ابزاری اجرا نمی‌شود.
3. **درخواست ساخت کوتاه** («یه بازی شطرنج بساز») → پیش از هر طرحی چند سؤال ثابت و مرتبط (ظاهر، اندازهٔ پنجره، حالت/کنترل، امکانات) با پیش‌فرض می‌پرسد؛ آنچه قبلاً گفته‌اید دوباره پرسیده نمی‌شود. با «پیش‌فرض‌ها خوبه» یا «بدون سوال» مستقیم به طرح می‌رود. هیچ سؤال بی‌ربطی (مثل قیمت) پرسیده نمی‌شود.
4. **بازخورد روی چیزی که ساخته شده** («گرافیکی نیست»، «صفحه کوچک است»، «تغییری نکرد») → حالت ویرایش: کد واقعی پروژه به مدل نشان داده می‌شود، همان پروژه ویرایش می‌شود (پروژهٔ تازه ساخته نمی‌شود) و فایل‌های لازم از جمله main.py تغییر می‌کنند.
5. پس از تأیید طرح، مدل مرحله‌ها را اجرا می‌کند و پیشرفت را در همان گفت‌وگو می‌نویسد.

## سطح دسترسی ابزارها

| گروه | ابزارها | تأیید |
|---|---|---|
| فقط‌خواندنی | `read_file`، `list_files`، `list_projects`، `check_environment`، `check_project` | بدون پرسش |
| نوشتن در پوشهٔ پروژه | `create_project`، `create_venv`، `write_file`، `update_file`، `edit_file`، `create_launcher` | با تأیید طرح می‌توانید «نوشتن خودکار» را روشن کنید؛ وگرنه هر مورد جداگانه |
| اجرا | `venv_install`، `venv_run`، `venv_test`، `docker_test`، `docker_run`، `screenshot_check`، `open_in_editor` | **همیشه** تأیید جداگانه با نمایش دقیق دستور |

- پروژه‌ها در `%LOCALAPPDATA%\LocalChat\projects\<نام>` ساخته می‌شوند. فایل‌ها فقط در `src`، `tests`، `data`، `assets`، `docs` (و `requirements.txt`، `README.md`، `.gitignore` در ریشه) و فقط با پسوند متنی.
- `edit_file` یک بخش یکتای فایل را عوض می‌کند (برای رفع باگ)، `update_file` کل فایل را. هر دو نسخهٔ قبلی را در `.history/` نگه می‌دارند و قبل از تأیید diff نشان داده می‌شود.
- هیچ فرمان shell، PowerShell یا CMD اجرا نمی‌شود؛ همهٔ دستورها لیست آرگومان ثابت‌اند.

## محیط مجازی و کتابخانه‌ها

- `create_venv` با Python واقعی سیستم (نه خود برنامهٔ نصبی) `.venv` می‌سازد. اگر Python نصب نباشد پیام روشن می‌دهد.
- `venv_install` فقط از PyPI و فقط با wheel آماده نصب می‌کند (`--only-binary=:all:`)، سپس `requirements.txt` را با نسخهٔ نصب‌شده به‌روز می‌کند. نصب از سورس عمداً مجاز نیست.
- `venv_run` فایل `src/...py` را با venv پروژه اجرا می‌کند (حداکثر ۱۲۰ ثانیه). این اجرا روی خود رایانه است و sandbox نیست؛ پس همیشه تأیید می‌خواهد.
- `venv_test` تست‌ها را با pytest (اگر نصب باشد) یا unittest اجرا می‌کند؛ برای pygame از SDL بدون پنجره استفاده می‌شود.
- `create_launcher` یک `run.bat` ثابت می‌سازد که با دو بار کلیک برنامه را با venv پروژه اجرا می‌کند (محتوایش را مدل تعیین نمی‌کند).

## Docker (اختیاری، ایزوله‌تر)

`docker_test` و `docker_run` فقط جریان ثابتِ زیر را اجرا می‌کنند و هیچ آرگومان Docker، image یا مسیر دلخواهی از مدل نمی‌پذیرند:

1. اگر image `python:3.12-slim` نباشد دانلود می‌شود.
2. اگر `requirements.txt` بسته دارد، در یک کانتینر جدا فقط wheelهای باینری از PyPI دانلود می‌شود (این کانتینر کد پروژه را نمی‌بیند).
3. تست یا اسکریپت در کانتینر دوم **بدون شبکه** اجرا می‌شود؛ پروژه فقط‌خواندنی mount و در tmpfs کپی می‌شود؛ وابستگی‌ها آفلاین نصب می‌شوند.
4. کانتینرها محدودیت CPU/حافظه/PID دارند، capabilityها حذف شده‌اند و پس از پایان یا timeout حتماً حذف می‌شوند.

برنامه‌های گرافیکی/تعاملی در Docker اجرا نمی‌شوند؛ منطقشان تست می‌شود و با `run.bat` اجرا می‌گردند. اگر Docker نصب نباشد، `venv_test` جایگزین است.

## امنیت نشست

هر درخواست حساس باید Origin محلی، کوکی HttpOnly/SameSite=Strict و توکن CSRF همان نشست را داشته باشد. تأییدها یک‌بار‌مصرف، متعلق به همان نشست و تا ۱۰ دقیقه معتبرند. دکمهٔ توقف، گفت‌وگو، انتظار تأیید و فرایندهای در حال اجرا را متوقف می‌کند.

## راستی‌آزمایی بازی‌ها (اسکرین‌شات + مدل بینایی)
- `check_project` بدون اجرای کد، ساختار را می‌خواند: خطای نحوی، ماژول‌هایی که main.py هرگز import نمی‌کند، تابع‌های خالی، کتابخانهٔ import‌شده که در requirements.txt نیست، کامل نبودن حلقهٔ pygame.
- `screenshot_check` برنامهٔ pygame را چند ثانیه بدون پنجره اجرا می‌کند، در صورت درخواست کلیک و کلید شبیه‌سازی می‌کند و عکس می‌گیرد (`output/screenshots`). گزارش: اندازهٔ پنجره، تعداد فریم، رنگ‌های غالب و اینکه پس از هر کلیک تصویر تغییر کرده یا نه. اگر مدل بینایی نصب باشد (یا مدل انتخاب‌شده بینایی داشته باشد) عکس را بررسی و توضیح می‌دهد.
- اجرای بدون خطای برنامهٔ گرافیکی دیگر «موفق» گزارش نمی‌شود مگر با همین شواهد.

## برنامه‌های نصب‌شده روی رایانه
`check_environment` Python، Docker، VS Code، Flutter، Dart، Gradle، Java، Node/npm، Git، adb و dotnet را هم در PATH و هم در پوشه‌های معمول (Program Files، LOCALAPPDATA، C:\flutter، ~\flutter، JAVA_HOME، ANDROID_HOME و …) پیدا می‌کند. Docker خارج از PATH هم استفاده می‌شود. برای مسیر غیرمعمول فایل `%LOCALAPPDATA%\LocalChat\tool_paths.json` را بسازید:
```json
{"docker": "D:\\Tools\\Docker\\resources\\bin\\docker.exe", "code": "D:\\VSCode\\bin\\code.cmd", "flutter": "E:\\dev\\flutter\\bin\\flutter.bat"}
```
فعلاً مدل می‌تواند پروژه را در VS Code باز کند (`open_in_editor`، با تأیید). ساخت و اجرای پروژه‌های Flutter/Gradle/Node هنوز ابزار ندارد (فقط شناسایی و گزارش می‌شوند).

## 1.9.2: انواع پروژه، VS Code، انتخاب خودکار
- نوع پروژه: python (پیش‌فرض)، flutter، gradle، node (`create_project` با `kind`). ابزارهای venv/docker/screenshot فقط برای python؛ `toolchain_run` فقط برای بقیه.
- `toolchain_run(project, task, packages|platforms|type|dsl)`: وظایف فهرست‌سفید، بدون shell، با تأیید کاربر.
- `editor_setup` (نوشتن .vscode با نشانهٔ `// LocalChat generated`)، `editor_extension` (فهرست‌سفید)، `open_in_editor(project, path, line)`.
- طرح‌ساز `kind` و `stack_reason` را خودش انتخاب می‌کند؛ مدل بدون tool-calling خودکار با مدل مناسب جایگزین می‌شود.
